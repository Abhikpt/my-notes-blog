    Introduction

    Four Dimensions of Software Architecture

    Dimension Description Example
    Structure Organization of system components. Microservices vs. Monolith.
    Behavior Interaction between components. REST APIs, Event-Driven Messaging.
    Quality Attributes Non-functional requirements (NFRs). Scalability, Security, Performance.
    Development & Evolution Maintainability and adaptability over time. CI/CD pipelines, Modular design.

    Architecture Decision vs. Design Principle

    Aspect Architecture Decision Design Principle
    Scope System-wide (e.g., database choice). Component-level (e.g., class structure).
    Impact Long-term, hard to change. Easier to refactor.
    Example "Use Kubernetes for orchestration." "Follow DRY (Don’t Repeat Yourself)."

    First Law of Software Architecture

    "Everything in software architecture is a trade-off."
    Example: Choosing between consistency (ACID) vs. scalability (BASE) in databases.

    Architectural Thinking

    Architecture vs. Design Decision Criteria

    Criterion Architecture Design
    Scope Affects entire system. Limited to a component.
    Longevity Years. Weeks/months.
    Reversibility Costly to change. Easily refactored.

    Three Levels of Knowledge

    1. Facts (What)
    2. "Containers isolate applications using kernel namespaces."
    3. Concepts (Why)
    4. "Isolation improves security and resource efficiency."
    5. Wisdom (How)
    6. "Use Docker with cgroups to limit CPU usage."

    Maintaining Technical Depth

    • Practice: Contribute to open-source (e.g., Kubernetes).
    • Review: Conduct code reviews focusing on architectural fit.
    • Experiment: Build POCs with new tech (e.g., Serverless).

    Modularity & Design

    Coupling vs. Cohesion

    Concept Goal Anti-Pattern Solution
    Coupling Minimize dependencies. ClassA directly modifies ClassB’s data. Use interfaces (Dependency Inversion).
    Cohesion Maximize relatedness. User class handles auth + logging. Split into AuthService and Logger.

    Connascence: Types & Mitigation

    Type Strength Example Mitigation
    Name (Weakest) Low Naming conventions. Enforce style guides.
    Position Medium Method parameter order. Use named parameters (C#).
    Identity (Strongest) High Global variables. Dependency Injection.

    Rule: Prefer static (compile-time) over dynamic (runtime) connascence.

    Architecture Characteristics Defined

    Criteria for Characteristics

    1. Cross-Cutting Impact
    2. Example: Security affects APIs, databases, and networking.
    3. Architectural Trade-offs
    4. Example: High availability vs. cost (multi-region deployment).
    5. Explicit vs. Implicit
    6. Explicit: "System must handle 10K RPS."
    7. Implicit: "Code must be readable."

    Operational vs. Structural

    Category Examples Tools/Patterns
    Operational Latency, Fault Tolerance. Load balancers, Circuit Breakers.
    Structural Modularity, Configurability. Microservices, Plugin Architecture.

    Software design:

    1. SOLID Design Principles:

    SOLID is a set of five design principles aimed at making software designs more maintainable, flexible, and scalable.

    Principle Full Form Description
    S Single Responsibility Principle A class should have only one reason to change; it should have only one responsibility.
    O Open/Closed Principle Classes should be open for extension but closed for modification.
    L Liskov Substitution Principle Subclasses should be substitutable for their base classes without altering program correctness.
    I Interface Segregation Principle A class should not be forced to implement interfaces it does not use.
    D Dependency Inversion Principle High-level modules should depend on abstractions, not on concrete implementations.

    1.1 Single Responsibility Principle (SRP)

    • A class should have only one responsibility (i.e., only one reason to change).

    Why?

    • Reduces complexity
    • Improves maintainability
    • Makes code easier to test

    How?

    • Split classes that handle multiple responsibilities into smaller, focused classes.

    Example

    // ❌ Violation: Mixes user logic + file I/O
public class User
{
    public string Name { get; set; }
    public void SaveToFile(string path) { File.WriteAllText(path, Name); }
}

// ✅ Correct: Separated concerns
public class User { public string Name { get; set; } }
public class UserFileManager { public void SaveToFile(User user, string path) { ... } }

    Explanation: The first class violates SRP by combining user data storage and file operations. The corrected version splits these into two classes, each with a single responsibility.

    1.2 Open/Closed Principle (OCP)

    • Software entities should be open for extension but closed for modification.

    Why?

    • Prevents breaking existing code
    • Encourages reusable, modular design

    How?

    • Use abstractions (interfaces, abstract classes) and inheritance.

    Example

    // ❌ Violation: Modifying existing code for new shapes
public class AreaCalculator
{
    public double CalculateArea(object shape)
    {
        if (shape is Rectangle r) return r.Width * r.Height;
        else if (shape is Circle c) return Math.PI * c.Radius * c.Radius;
        // Must modify for new shapes!
    }
}

// ✅ Correct: Extensible via interfaces
public interface IShape { double Area(); }
public class Rectangle : IShape { public double Width, Height; public double Area() => Width * Height; }
public class Circle : IShape { public double Radius; public double Area() => Math.PI * Radius * Radius; }

    Explanation: The first example requires modifying AreaCalculator for new shapes. The second allows adding new shapes without changing existing code.

    1.3 Interface Segregation Principle (ISP) —

    • The Interface Segregation Principle is one of the SOLID principles of object-oriented design.
    • It helps you build clean, maintainable, and flexible systems.
    • It Says Clients should not be forced to depend on interfaces they do not use. i.e. Don’t create fat interfaces — instead, split them into smaller, more specific ones so that classes only implement what they really need.

    Bad Example(violate ISP)

        //Below implementation violate ISP
    public interface IMachine
    {
        void Print(Document d);
        void Scan(Document d);
        void Fax(Document d);
    }

    public class OldPrinter : IMachine
    {
        public void Print(Document d) { /* OK */ }
        public void Scan(Document d) { throw new NotImplementedException(); }
        public void Fax(Document d) { throw new NotImplementedException(); }
    }
    • Here OldPrinter don't have capability to do Scan or Fax so we should not show option scan and Fax to user as per ISP.

    Good Example (Follows ISP):

    // break down the interfaces
public interface IPrinter
{
    void Print(Document d);
}

public interface IScanner
{
    void Scan(Document d);
}

public interface IFax
{
    void Fax(Document d);
}


// implement only what needs:

public class SimplePrinter : IPrinter
{
    public void Print(Document d) => Console.WriteLine("Printing...");
}

public class MultiFunctionPrinter : IPrinter, IScanner, IFax
{
    public void Print(Document d) => Console.WriteLine("Printing...");
    public void Scan(Document d) => Console.WriteLine("Scanning...");
    public void Fax(Document d) => Console.WriteLine("Faxing...");
}
    • Now each class implements only the feature it actually supports.

    ## Dependency Inversion and Dependency Injection Principles

    🔗 Dependency

    • A dependency means one class relies on another to perform a function.
    • This leads to tight coupling, where changing one class may affect the other.

    🔄 Coupling

    • Coupling measures how closely two classes or modules are connected.
    • High coupling makes the system rigid and difficult to test or extend.
    • Good software design promotes loose coupling for flexibility and maintainability.

    💡 Dependency Injection (DI)

    • A design pattern used to reduce coupling between classes.
    • Instead of a class instantiating its dependencies, they are injected from outside.
    • Follows the Dependency Inversion Principle: High-level modules should not depend on low-level modules; both should depend on abstractions.

    🧱 DI Involves 3 Types of Classes

    Type Description
    Client Class The dependent class that uses a service (e.g., EmployeeBusinessLogic).
    Service Class The class that provides the service or functionality (e.g., EmployeeDbService).
    Injector Class Supplies the service class object to the client (can be the Main() method).

    We use interfaces to define the contract of the service. This allows the client to remain unaware of which concrete implementation (e.g., SQL, Oracle, Excel) is being used.

    🛠️ Types of Dependency Injection

    1. Constructor Injection

    • The Injector Injects the Dependency Object (i.e. Service Object) into the Client Class through the Client Class Constructor.
    • Ensures the class gets its required dependency at initialization.
    public class EmployeeBusinessLogic
{
    private readonly IEmployeeDbService _employeeDbService;

    public EmployeeBusinessLogic(IEmployeeDbService employeeDbService)
    {
        _employeeDbService = employeeDbService;
    }

    public List<Employee> GetAllEmployees() => _employeeDbService.SelectAllEmployees();
}

// Usage in Main
var service = new EmployeeDbService();
var logic = new EmployeeBusinessLogic(service);
logic.GetAllEmployees();

    2. Property Injection (Setter Injection)

    • When the Injector Injects the Dependency Object (i.e. Service Object) into the Client Class through the public Property of the Client Class, then it is called Property Dependency Injection. This is also called the Setter Injection.
    • Useful when the dependency is optional or needs to change.
    public class EmployeeBusinessLogic
{
    public IEmployeeDbService EmployeeDataService { private get; set; }

    public List<Employee> GetAllEmployees()
    {
        return EmployeeDataService.SelectAllEmployees();
    }
}

// Usage
var logic = new EmployeeBusinessLogic();
logic.EmployeeDataService = new EmployeeDbService();
var employees = logic.GetAllEmployees();

    3. Method Injection

    • When the Injector Injects the Dependency Object (i.e. Service Object) into the Client Class through a public Method of the Client Class, then it is called Method Dependency Injection.
    • Flexible but may make method signatures more verbose.
    public class EmployeeBusinessLogic
{
    public List<Employee> GetAllEmployees(IEmployeeDbService employeeService)
    {
        return employeeService.SelectAllEmployees();
    }
}

// Usage
var logic = new EmployeeBusinessLogic();
var employees = logic.GetAllEmployees(new EmployeeDbService());

    ✅ Benefits of Dependency Injection

    Benefit Description
    Loose Coupling Promotes separation of concerns and easier testing.
    Increased Testability Makes it easy to use mock or stub objects for unit testing.
    Better Maintainability Changes in one class require fewer (or no) changes in others.
    Easier Extensibility New implementations can be introduced without modifying client code.
    Adheres to SOLID Principles Encourages Single Responsibility and Dependency Inversion.

    2. Creational Patterns

    All of the creational patterns deal with ways to create instances of objects. This is important because your program should not depend on how objects are created and arranged. In C#, of course, the simplest way to create an instance of an object is by using the new operator.

    Fred fred1 = new Fred(); //instance of Fred class

    2.1 Singleton Pattern

    The Singleton pattern ensures that a class has only one instance and provides a global access point to it. [control object creation]

    Why:

    Ensures controlled access to a single resource (e.g., logger, configuration, caching). Saves memory and improves performance when one object is enough. Useful when only one instance is logically required (e.g., PrintSpooler, Database Connection Manager).

    Required Elements / Steps:

    Element Explanation In Your Example
    Private Constructor Prevents external classes from creating new instances using new. private Logger() { }
    Static Instance Variable Holds the single instance of the class. private static Logger _instance;
    Public Static Property Provides global access to the instance with lazy initialization. public static Logger Instance
    Thread Safety (optional) Ensures only one thread can create the instance in multi-threaded environments. lock (_lock)
    Sealed Class (C# specific) Prevents inheritance to protect Singleton behavior. public sealed class Logger

    How:

    Private constructor Static field to hold the instance Public static method/property to access the instance Thread safety (for multithreading scenarios)

    Example with Thread-safe

    public sealed class Logger
{
    private static Logger _instance;
    private static readonly object _lock = new();

    private Logger() { } // To Prevent external instantiation from other classes

    public static Logger Instance
    {
        get
        {
            lock (_lock) // Thread-safe
            {
                return _instance ??= new Logger();
            }
        }
    }

    public void Log(string message) => Console.WriteLine(message);
}

    Explanation:
    - lock ensures thread safety.
    - sealed prevents inheritance.
    - Usage: Logger.Instance.Log("Hello");

    2.2 Factory Method Pattern

    • Defines an interface for creating objects but lets subclasses decide which class to instantiate.

    Why?

    • Decouples client code from concrete classes
    • Simplifies adding new product types

    How?

    1. Creating Product Interface ICreditCard with method signature GetCardType, GetTotalAmount, GetAnaualCharge.
    2. Creating Concrete Products (MoneyBack, Titanium, and Platinum) and implement interface methods
    3. Creating Interface Creator (ICreditCardFactory). The Abstract Creator declares the factory method, which returns an object of type Product.
    4. Creating Concrete Creator(PlatinumFactory, MoneyBackFactory, and TitaniumFactory) that implement Creator interface methods.
    5. Consuming the Factory Method in the Client Code.

    Example

    


public abstract class Document
{
    public List<Page> Pages { get; } = new();
    public abstract void CreatePages(); // Factory method
}

public class Resume : Document
{
    public override void CreatePages()
    {
        Pages.Add(new SkillsPage());
        Pages.Add(new EducationPage());
    }
}

public class Report : Document
{
    public override void CreatePages()
    {
        Pages.Add(new SummaryPage());
        Pages.Add(new ConclusionPage());
    }
}

    Explanation:
    - Resume and Report are concrete creators that implement CreatePages().
    - Clients use Document without knowing the concrete page types.

    2.3 Factory Design Pattern

    The Factory Design Pattern is a creational design pattern that provides an interface for creating objects in a superclass, but allows subclasses to alter the type of objects that will be created. This pattern is particularly useful when the exact type of the object to be created is not known until runtime.

    Why?

    • Decouples client code from concrete classes, so that no need to modify the client code if changing Product details, removing the product etc.
    • Simplifies adding new product types
    • Allows clients to use interface/abstraction, not concrete classes.
    • Object creation logic is centralized in the factory.
    • Promotes the Open/Closed Principle (Open for extension, closed for modification).

    ✅ 1. Required Elements / Steps in Factory Design Pattern

    Element Explanation In Your Code
    Product Interface Defines the contract (common methods/properties) that all product types implement. ICreditCard
    Concrete Products Specific implementations of the product interface. MoneyBack, Platinum, Gold
    Factory Class (Creator) Contains logic to instantiate appropriate concrete class based on input/conditions. CreditCardFactory.GetCreditCard()
    Client Code Consumes the product interface, unaware of which concrete class was created. Main_ConsumeProducts() method

    How?

    • Define a Creator abstract class with a factory method.

    Example

    
namespace CSHARPCONCEPTS.CreationalDesignPattern;
public class FactoryDesignPattern
{
    // created product interface to expose operation a credit card should have
    public interface ICreditCard
    {
        string GetCardType();
        int GetCreditLimit();
    }

    // created concrete/Product classes (MoneyBack, Platinum, Gold) implementing the CreditCard interface
    public class MoneyBack : ICreditCard
    {
        public string GetCardType()
        {
            return "Money Back Credit Card";
        }

        public int GetCreditLimit()
        {
            return 50000;
        }
    }

    public class Platinum : ICreditCard
    {
        public string GetCardType()
        {
            return "Platinum Credit Card";
        }

        public int GetCreditLimit()
        {
            return 100000;
        }
    }

    // created a factory class to generate the object of concrete classes based on the information provided
    public class CreditCardFactory
    {
        public static ICreditCard GetCreditCard(string cardType)
        {
            if (cardType.Equals("MoneyBack"))
            {
                return new MoneyBack();
            }
            else if (cardType.Equals("Platinum"))
            {
                return new Platinum();
            }           
            else
            {
                Console.WriteLine("Invalid Card Type");
                return null;
            }
        }
    }    

    // consume the product classes inside the client code
    public static void Main_ConsumeProducts()
    {
        string cardType = "MoneyBack"; // input from UI
        ICreditCard creditCard = CreditCardFactory.GetCreditCard(cardType);

        // Displaying the card details
        if (creditCard != null)
        {
            Console.WriteLine("Card Type: " + creditCard.GetCardType());
            Console.WriteLine("Credit Limit: " + creditCard.GetCreditLimit());
            Console.WriteLine("Annual Charge: " + creditCard.GetAnnualCharge());
        }
        else
        {
            Console.WriteLine("Invalid Card Type");
        }
    } 
}

    Explanation:
    - MoneyBack and Platinu are concrete creators that implement cardlimit and getCardType.
    - Clients use CreditCardFactory without knowing the concrete page types.

    🚀 3. Benefits of Factory Design Pattern

    Benefit Explanation
    ✅ Loose Coupling Client code is not directly dependent on concrete classes.
    ✅ Centralized Object Creation Factory handles object creation, reducing duplication and improving maintainability.
    ✅ Improved Scalability New product types (e.g., TitaniumCard) can be added with minimal changes to client code.
    ✅ Easy Testing and Maintenance You can mock the interface ICreditCard during unit testing.
    ✅ Encapsulation of Complexity Complex object creation logic (e.g., configuration, dependencies) is hidden in the factory.
    ✅ Run-Time Decision Making Objects can be created based on input/configuration received at runtime (like UI input).

    3. Behavioral Patterns

    3.1 Observer Pattern

    • Defines a one-to-many dependency between objects so that when one object changes state, all dependents are notified.

    Why?

    • Enables event-driven systems
    • Loose coupling between subjects and observers

    How?

    • Use IObservable<T>/IObserver<T> or custom interfaces.

    Example

    public class WeatherStation : IObservable<WeatherData>
{
    private List<IObserver<WeatherData>> _observers = new();

    public IDisposable Subscribe(IObserver<WeatherData> observer)
    {
        _observers.Add(observer);
        return new Unsubscriber(_observers, observer);
    }

    public void UpdateWeather(WeatherData data)
    {
        foreach (var observer in _observers)
            observer.OnNext(data);
    }
}

public class Display : IObserver<WeatherData>
{
    public void OnNext(WeatherData data) => Console.WriteLine($"Temp: {data.Temperature}°C");
}

    Explanation:
    - WeatherStation (subject) notifies Display (observer) when weather changes.
    - Built-in IObservable<T> handles subscriptions.
