    🧬 Evolution of DevOps

    1. Waterfall Model

    • Complete development first, then deployment.
    • Difficult to accommodate changes.
    • Large gap between development and operations.

    2. Agile Method

    • Build small, build often.
    • Enables frequent changes and feedback.
    • Still maintains a gap between dev and ops teams.
    • Provide frequent business deliverables on a monthly or sprint basis.
    • Each sprint includes:
    • Development → Build → Test → Deploy
    • This iterative process is known as Scrum.
    • Agile is a methodology; Scrum is one of its implementations.

    3. Microsoft DevOps

    • Supports incremental development and continuous changes.
    • Developers and operations work on a single integrated platform.

    🚀 DevOps Core Concepts

    • All steps (develop → build → test → deploy → monitor) are continuous.
    • Integrates development and operations into a unified, automated pipeline.

    Basics of deployment:

    Application deployment is the process of making an application available for users to access and use. It involves transferring the built application from the development environment to a server or cloud platform where it can be run and accessed by users. Here’s a basic overview of the deployment process:

    1. Understand the Types of Deployment

    • Manual Deployment: The developer manually copies application files to the target server and configures the necessary settings. This method is more error-prone but is suitable for simple applications. • Automated Deployment: Tools like Jenkins, GitHub Actions, or Azure DevOps automate the deployment process to minimize errors and improve efficiency.

    2. Deployment Environments

    Applications are deployed to different environments for different purposes: • Development Environment: Used by developers to code and test new features. • Testing/Staging Environment: A replica of production where QA can test the application before it goes live. • Production Environment: The live environment accessible by end-users.

    3. Deployment Steps

    Here are the typical steps involved in deploying an application:

    a. Build the Application
    • Build Process: Compile the source code into a format that can be run by a server (e.g., an executable or a set of static files). • Package: Bundle the built application into a package or an archive (e.g., .zip, .tar, .war, .dll).

    b. Prepare the Target Server
    • Provisioning: Set up the server (physical or virtual) where the application will run. This could be a dedicated server, a cloud instance, or a container. • Configure Dependencies: Install necessary dependencies such as runtimes (e.g., .NET Core, Java, Node.js), libraries, and other services the application needs.

    c. Transfer Files
    • Transfer the built files to the target server using tools like: o FTP/SFTP: For file transfer between local machines and remote servers. o SSH: Secure shell for accessing servers and copying files (scp). o Deployment Tools: Tools like rsync, Ansible, or container registries for Docker images.

    d. Configuration
    • Environment-Specific Configurations: Set environment-specific configurations, such as database connection strings, API keys, etc. • Environment Variables: Use environment variables to avoid hard-coding sensitive information in your codebase.

    e. Start the Application
    • Web Servers: Deploy the application to a web server like Apache, NGINX, IIS, or Kestrel for serving HTTP requests. • Containers: Deploy as Docker containers using Docker Compose or orchestration tools like Kubernetes. • Cloud Services: Deploy to cloud services like Azure App Service, AWS Elastic Beanstalk, or Google App Engine for easy scaling and management.

    f. Monitoring & Testing
    • Smoke Testing: After deployment, perform basic tests to ensure the application is running correctly. • Monitoring: Set up monitoring for your application to track uptime, performance, and errors. Tools like Prometheus, Grafana, or cloud-native monitoring solutions can help.

    4. Deployment Models

    • Rolling Deployment: Gradually update parts of the application so that there is no downtime. This helps ensure that users still have access during the update. • Blue-Green Deployment: Set up two identical environments (blue and green). Deploy to one environment, and if everything works fine, switch traffic from the old environment to the new one. • Canary Deployment: Roll out the new version to a small subset of users first before a full-scale rollout. This approach helps minimize the impact of potential issues.

    5. CI/CD in Deployment

    • Continuous Integration (CI): Automatically build and test code changes whenever developers push code to version control. • Continuous Deployment (CD): Automatically deploy changes that pass tests to the production environment. This provides a seamless flow from development to production.

    6. Deployment Tools

    • Jenkins: Automate build, test, and deployment processes. • GitHub Actions: Run workflows to build, test, and deploy directly from GitHub. • Docker: Containerize applications for easy deployment across different environments. • Kubernetes: Automate deployment, scaling, and management of containerized applications. • Ansible/Chef/Puppet: Automate server setup, configuration, and deployment.

    Application / Software server vs Servers:

    Application servers are specialized software that provides an environment for applications to run, manage business logic, and facilitate communication between the client and the database or backend services.

    Application Server Options by Language

    This document provides an overview of common application server options based on programming language, along with their descriptions and typical use cases.

    C

    Application Server Description and Use Cases
    Kestrel Default ASP.NET Core server, often used with Nginx/Apache as a reverse proxy.
    IIS Enterprise server for Windows environments.
    Azure App Service Managed cloud hosting for .NET apps.
    NGINX/Apache with Kestrel Reverse proxy for handling traffic, SSL, and load balancing.

    Python

    Application Server Description and Use Cases
    Gunicorn WSGI server for Flask, Django, etc., often with NGINX.
    uWSGI Flexible WSGI server paired with NGINX for scalability.
    Apache HTTP Server with mod_wsgi Hosts Python web applications using Apache.
    Daphne Used for real-time Django applications.

    Java

    Application Server Description and Use Cases
    Apache Tomcat Lightweight, popular for JSP/Servlet applications.
    WildFly Java EE application server for enterprise-grade apps.
    Apache TomEE Tomcat with Java EE capabilities.
    GlassFish Full Java EE server, good for development and testing.
    Jetty Lightweight, ideal for embedded or microservices deployment.

    Notes

    Actual servers are the physical or virtual machines that host these application servers, providing the necessary infrastructure and resources for applications to operate.

    CI (Continuous Integration): Continuous Integration is the practice of frequently integrating code changes into a shared repository. Each integration is verified by automated builds and tests to detect issues early in the development process. Key Features: 1. Frequent Commits: Developers commit code changes regularly (multiple times a day) to the shared repository. 2. Automated Builds: Each commit triggers an automated build process, compiling the code to ensure it can be built without errors. 3. Automated Testing: Automated tests (unit tests, integration tests) are executed to verify that the new code does not break existing functionality. 4. Immediate Feedback: Developers receive quick feedback on the success or failure of their changes, allowing for prompt bug fixes.

    CD (Continuous delivery):

    Continuous Deployment takes Continuous integration a step further by automatically deploying every change that passes automated testing directly to production without manual intervention. Key Features: 1. No Manual Approval: Changes are deployed to production automatically once they pass the testing phase. 2. Frequent Releases: The application can be updated multiple times a day, enabling rapid delivery of new features, improvements, and fixes. 3. Monitoring and Rollback: Continuous deployment typically includes monitoring and rollback mechanisms to quickly address any issues that arise in production.

    Building CI with Azure pipelines:

    • Azure Pipelines is a cloud-based service provided by Microsoft Azure that enables you to automate the building, testing, and deployment of your applications. • It is a key component of Azure DevOps, which provides a comprehensive set of development tools and services for managing the entire software development lifecycle. • Azure Pipelines supports various programming languages, platforms, and cloud environments, making it a versatile choice for CI/CD practices.

    Key Features of Azure Pipelines

    1. Continuous Integration (CI): o Automate the building and testing of code changes when they are pushed to a version control system (like GitHub, Azure Repos, etc.). o Supports various build agents, including Windows, Linux, and macOS.
    2. Continuous Deployment (CD): o Automatically deploy applications to various environments (development, testing, production) based on defined triggers and conditions. o Integrates with Azure services and third-party services for seamless deployment.
    3. Multi-Platform Support: o Supports a wide range of programming languages, including .NET, Java, Python, Node.js, and more. o Can deploy applications to various platforms such as Azure App Services, Kubernetes, virtual machines, and other cloud services.
    4. Pipeline as Code: o Define your CI/CD pipeline using YAML configuration files, allowing versioning and easier management of your pipeline configuration. o YAML pipelines provide a more flexible and powerful way to define the build and release process.
    5. Integration with Other Tools: o Integrates seamlessly with Azure DevOps Services, GitHub, Docker, Jenkins, and other tools and services, allowing for a more robust development workflow. o Supports the use of custom tasks and extensions to enhance the pipeline capabilities.
    6. Multi-Stage Pipelines: o Support for creating multi-stage pipelines, allowing you to define various stages (build, test, deploy) in a single YAML file. o Enables complex workflows with conditions and approvals between stages.
    7. Environment Management: o Manage deployment environments directly within Azure Pipelines, allowing you to define different configurations and approvals for production deployments.

    Basic terms / tool on ADO board:

    1. Pipeline: A definition of the steps needed to build, test, and deploy your application. Can be defined in the Azure DevOps portal or through a YAML file.
    2. Build Pipeline: Automates the build process, including compiling code, running tests, and packaging the application.
    3. Release Pipeline: Automates the deployment of applications to various environments.
    4. Agent: A software component that runs the tasks in your pipeline. Azure provides hosted agents, or you can set up self-hosted agents.
    5. Task: A single unit of work that does something, like compiling code or running tests.

    Setting Up Azure Pipelines

    1. Create an Azure DevOps Organization: o Go to the Azure DevOps website and create a new organization if you don't have one.
    2. Create a New Project: o Within your Azure DevOps organization, create a new project to house your pipeline.
    3. Create a Pipeline: o Go to the Pipelines section and select "New Pipeline." o Follow the wizard to connect your repository (e.g., GitHub, Azure Repos) and select the YAML file or configure your pipeline.
    4. Run the Pipeline: o Once the pipeline is created, you can manually trigger it or let it run automatically based on the defined triggers.

    Example of a Basic YAML Pipeline

    Here’s a simple example of a YAML pipeline that builds a .NET application:

    trigger:
  - main

pool:
  vmImage: 'windows-latest'

steps:
- task: DotNetCoreCLI@2
  inputs:
    command: 'build'
    projects: '**/*.csproj'
    versioningScheme: 'byBuildNumber'
    publishWebProjects: true

- task: DotNetCoreCLI@2
  inputs:
    command: 'test'
    projects: '**/*.csproj'

    Breakdown of the YAML Pipeline

    1. trigger: Defines the branch that triggers the pipeline. In this case, it triggers on the main branch.
    2. pool: Specifies the type of agent to use. Here, it uses a hosted Windows agent.
    3. steps: Lists the tasks to be executed in the pipeline: o The first task uses the DotNetCoreCLI task to build all .csproj projects. o The second task runs tests on all .csproj projects.

    Publish your webapp:

    Hosting a static Website on GitHub:

    1. Create a GitHub account on github.com.
    2. Download either GitHub for Mac or GitHub for Windows, depending on your operating system. Open the app and log in using the account you just created.
    3. (On Mac): After you login, click advanced and make sure that your name and email are correct. Then, click "Install Command Line Tools", just in case you want to start using the command line later in life.
    4. Create a new repository in your GitHub application. Name it your-username.github.io. The name is very important. Note the folder that GitHub is saving the repository to. Make sure the "Push to GitHub?" box is checked.
    5. Move your website's files into the folder that GitHub just created when you made the repository. IMPORTANT: Your homepage HTML file must be called "index.html", and it must exist in the top-level directory.
    6. Back in the GitHub application, you should see your files in the left column. Make sure they are all checked. If so, enter a message in the text box called "commit summary", something like "initial commit." Then, click the commit button.
    7. Click the "Publish repo" button in the top right corner.
    8. Give it about 10 minutes, then check your-username.github.io. Your website should be there!

    Publish blazer App on GitHub;

    • Deployed using GitHub Action • Create workflow • Main.yml file

    name: Deploy blazor app to GitHub Pages

# Run workflow on every push to the master branch
on:
  push:
    branches: [master]

jobs:
  deploy-to-github-pages:
    # use ubuntu-latest image to run steps on
    runs-on: ubuntu-latest
    steps:
    # uses GitHub's checkout action to checkout code form the master branch
    - uses: actions/checkout@v2

    # Setup .NET Core SDK 3.1
    - name: Setup .NET Core SDK
      uses: actions/setup-dotnet@v1
      with:
        dotnet-version: 6.x
        include-prerelease: true

    # publishes Blazor project to the release-folder
    - name: Publish .NET Core Project
      run: dotnet publish LearningwithAbhi.sln -c Release -o release --nologo

    # changes the base-tag in index.html from '/' to 'LearningwithAbhi' to match GitHub Pages repository subdirectory
    - name: Change base-tag in index.html from / to LearningwithAbhi
      run: sed -i 's/<base href="\/" \/>/<base href="\/LearningwithAbhi\/" \/>/g' release/wwwroot/index.html

    # copy index.html to 404.html to serve the same file when a file is not found
    - name: copy index.html to 404.html
      run: cp release/wwwroot/index.html release/wwwroot/404.html

    # add .nojekyll file to tell GitHub pages to not treat this as a Jekyll project. (Allow files and folders starting with an underscore)
    - name: Add .nojekyll file
      run: touch release/wwwroot/.nojekyll

    - name: Commit wwwroot to GitHub Pages
      uses: JamesIves/github-pages-deploy-action@3.7.1
      with:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        BRANCH: gh-pages
        FOLDER: release/wwwroot
